# 1. Огляд системи

MovieHarbor — LLM-орієнтована рекомендаційна система фільмів у формі діалогового сервісу, розроблена як proof of concept (PoC) магістерської роботи. Система реалізує двоетапний пайплайн RAG (Retrieval-Augmented Generation): відбір кандидатів (retrieval) семантичним пошуком у каталозі з 2 274 фільмів і генерацію, заземлену на кандидатах (grounded generation), яку виконує велика мовна модель (Large Language Model, LLM).

Користувач описує бажане у вільній формі. Агент на основі LLM формулює пошуковий запит, отримує кандидатів, вирішує, чи показати трейлер, обирає фільми й пояснює вибір. За замовчуванням усі моделі працюють локально, у контейнерах Docker на комп'ютері користувача: Gemma 4 в Ollama і модель ембедінгів.

Архітектуру описано за моделлю [C4](https://c4model.com/) — від контексту системи до контейнерів, компонентів і розгортання. Детальний опис кожної частини наведено в окремих розділах (§1.5).

## 1.1. Ключові властивості

- **Агент із викликом інструментів (tool calling), а не генерація «з пам'яті».** LLM викликає `search_movies`, `show_trailer` (за власним рішенням) і `recommend`; код виконує пошук і перевіряє вибір ([розділ 3](03-llm-and-tool-calling.md)).
- **Заземлення (grounding).** Рекомендувати можна лише фільм, який повернув останній пошук у поточній репліці; вигадані id відхиляються, що захищає від галюцинацій (hallucinations) щодо об'єктів рекомендації ([розділ 8](08-hallucinations.md)).
- **Багатомовність.** Пошуковий запит формулюється мовою користувача, без перекладу; багатомовна модель ембедінгів зіставляє його з англійськими описами фільмів у спільному векторному просторі ([розділ 7](07-embedding-model.md)). Відповідь також генерується мовою користувача.
- **Локальний запуск за замовчуванням.** Типове джерело — мала модель `gemma4:e4b` в Ollama; промпт і схеми інструментів розраховано саме на неї ([розділ 3.10](03-llm-and-tool-calling.md#310-мала-локальна-модель)). Альтернативу — Gemma 4 26B через OpenRouter — обирають у перемикачі.
- **Спостережність.** Кожен крок агента передається в інтерфейс у процесі виконання. Бічна панель відображає пошуковий запит, кандидатів із косинусною подібністю, трейлер і вибір.
- **Вимірюваність.** Якість семантичного пошуку ([розділ 6](06-evaluation.md)) і вплив параметрів користувача ([розділ 9](09-selection-parameters.md)) виміряно на відтворюваних бенчмарках.
- **Простота.** Система не використовує ні векторної бази даних (Vector DB), ні збірки фронтенду: увагу зосереджено на алгоритмі рекомендацій, а не на інфраструктурі ([розділ 2.6](02-data-and-embeddings.md#26-чому-без-векторної-бази-даних)).

## 1.4. Рівень 3: компоненти бекенду

```mermaid
flowchart TB
    api["api.py<br/>[HTTP-шар] ендпоінти, Recommender:<br/>перевірка, агент, потік кроків"]
    settings["settings.py<br/>[HTTP-шар] налаштування,<br/>профілі джерел моделі"]
    agent["core/agent.py<br/>цикл агента"]
    prompts["core/prompts.py<br/>системний промпт, мова"]
    tools["core/tools.py<br/>виклик інструментів,<br/>заземлення"]
    llm["adapters/llm.py<br/>OpenAI-сумісний клієнт"]
    catalog["core/catalog.py<br/>фільми, пошук"]
    embedder["adapters/embedder.py<br/>ембедінги"]
    tmdb["adapters/tmdb.py<br/>трейлери"]

    api --> settings
    api --> agent
    agent --> prompts
    agent --> tools
    agent -. "Chat" .-> llm
    tools --> catalog
    tools -. "embed" .-> embedder
    tools -. "find_trailer" .-> tmdb

    classDef web fill:#dbe8f6,stroke:#2e6295,color:#000
    classDef core fill:#438dd5,stroke:#2e6295,color:#fff
    classDef adapter fill:#bbb,stroke:#6b6b6b,color:#000
    class api,settings web
    class agent,prompts,tools,catalog core
    class llm,embedder,tmdb adapter
```

Синім позначено ядро (`core`), сірим — адаптери зовнішніх сервісів, світлим — HTTP-шар. Суцільна стрілка позначає прямий виклик, пунктирна — залежність через інтерфейс: адаптер створює `api.py` і передає ядру як функцію чи об'єкт (`Chat`, `embed`, `find_trailer`).

Імпорти спрямовано до ядра. `core` не імпортує ні FastAPI, ні HTTP-клієнтів, ні адаптерів; це перевіряє `tests/test_architecture.py`. Адаптери, навпаки, імпортують типи ядра: `llm.py` перетворює відповідь сервера на `ToolCall` і `AssistantTurn` з `core/tools.py`. Завдяки цьому ядро тестується без мережі на детермінованих подвійниках, а заміна провайдера моделі чи джерела трейлерів не зачіпає логіки рекомендацій.

| Компонент | Відповідальність |
|---|---|
| `api.py` | контракт HTTP: моделі запиту й відповіді, коди помилок, `Recommender` (перевірка запиту, запуск агента, потік кроків), роздача `frontend/` у локальній розробці |
| `settings.py` | змінні оточення й `.env`; профіль джерела моделі (`local` / `openrouter`) |
| `core/agent.py` | до 6 звернень до LLM на репліку; завершення лише через прийнятий `recommend`; повідомлення про кожен крок |
| `core/tools.py` | **виклик інструментів**: схеми з pydantic, обробники `search_movies`, `show_trailer`, `recommend`, заземлення, дані трасування |
| `core/prompts.py` | системний промпт, мова відповіді (`reply_language`), розмова як контекст, профіль користувача |
| `core/catalog.py` | `Movie`, `Catalog`: завантаження, атомарний запис, пошук за косинусною подібністю (cosine similarity) із жанровим фільтром |
| `adapters/llm.py` | `POST /chat/completions`, розбір викликів інструментів, українські повідомлення про помилки |
| `adapters/tmdb.py` | YouTube-трейлер фільму за TMDB id |
| `adapters/embedder.py` | модель ембедінгів через fastembed; кеш `models/embeddings/` |

## 1.7. Межі проєкту

PoC свідомо не включає облік користувачів, збереження історії на сервері, колаборативну фільтрацію (даних про перегляди немає, тобто система працює в умовах холодного старту (cold-start)), векторну БД і автоматичну оцінку якості пояснень LLM. Кожен із цих елементів можна додати без змін ядра: пошук ізольовано в `Catalog.search`, джерела моделі — у профілях, зовнішні сервіси — в адаптерах.

## 1.8. Розгортання (Docker Compose)

Рівень розгортання C4 показує, які процеси і де виконуються, коли систему запущено командою `docker compose` на комп'ютері користувача. За замовчуванням інференс і моделі ембедінгів, і LLM виконується локально, без платного API.

```mermaid
flowchart TB
    browser(["Браузер користувача<br/>127.0.0.1:8000"])

    subgraph host["Docker"]
        frontend["frontend (nginx)<br/>статичний інтерфейс,<br/>проксі /api/ без буферизації"]
        backend["backend<br/>FastAPI, агент, пошук;<br/>модель ембедінгів в образі"]
        ollama["ollama<br/>gemma4:e4b;<br/>GPU — compose.gpu.yaml"]
        oinit["ollama-init (одноразовий)<br/>ваги з кешу → том,<br/>pull за потреби, прогрів"]
        vol[("том ollama<br/>ваги моделі")]
    end

    data[("data/<br/>raw → movies.json, vectors")]
    cache[("models/ollama<br/>кеш проєкту")]
    or["OpenRouter (альтернатива)"]
    tmdb["TMDB API і CDN, YouTube"]

    browser --> frontend
    frontend -- "/api/" --> backend
    backend <--> data
    backend -- "ollama:11434/v1" --> ollama
    oinit --> ollama
    oinit <--> cache
    ollama --- vol
    backend -. "LLM_API_KEY" .-> or
    backend -- "TMDB_API_KEY" --> tmdb
    browser -- "постери, відео" --> tmdb
```

| Сервіс | Образ / файл | Що робить | Порт |
|---|---|---|---|
| `frontend` | `frontend/Dockerfile`, `frontend/nginx.conf` | роздає інтерфейс; проксує `/api/` до бекенду без буферизації (потік кроків), таймаут 600 с | `127.0.0.1:8000` |
| `backend` | `backend/Dockerfile` | API й агент; під час старту `scripts.prepare_data` будує каталог у змонтованій `data/`, якщо його немає | `127.0.0.1:8001` (API і `/docs` окремо) |
| `ollama` | `ollama/ollama:0.40.13` | локальна LLM; ваги в іменованому томі | — |
| `ollama-init` | `ollama/ollama:0.40.13` | одноразово: ваги з `models/ollama/` → том, `ollama pull`, лише якщо моделі ще немає, копія назад у кеш, прогрів моделі, якщо її ще не завантажено | — |

Рішення щодо розгортання:

- **Фронтенд і бекенд — окремі автономні сервіси.** nginx визначає адресу бекенду за іменем під час кожного запиту, тому фронтенд запускається й без нього. Поки бекенд стартує, сторінка показує «Сервер MovieHarbor ще запускається…» і підключається автоматично. У локальній розробці (`python -m backend`) ті самі файли роздає сам бекенд.
- **Бекенд стартує, щойно Ollama працює**, а не після завантаження ваг: OpenRouter доступний одразу, а локальна модель — після `ollama-init`. Сторінка пропонує локальну модель, лише коли Ollama вже перелічує її (`ready` у `/api/config`), тож перша репліка не очікує на незавантажені ваги.
- **Каталог — у змонтованій папці проєкту `data/`.** Під час першого старту каталог будується з `data/raw/` (≈ 3 хв на CPU; за наявності `TMDB_API_KEY` оновлюються й постери). Наступні старти використовують готові файли.
- **Моделі завантажуються один раз у кеш проєкту `models/`** (вміст у `.gitignore`, папки збережено через `.gitkeep`). Модель ембедінгів копіюється в образ бекенду (`HF_HUB_OFFLINE=1`: контейнер не звертається до Hugging Face). Ваги LLM `ollama-init` копіює з `models/ollama/` у том Docker і назад.
- **Ваги LLM читаються з тому Docker, а не з папки проєкту.** Ollama відображає ваги в пам'ять (mmap). Через файловий обмін Windows таке читання надто повільне: 5,5 ГБ не встигали завантажитися за 5-хвилинний ліміт Ollama (виміряно; послідовне читання — 86 МБ/с).
- **`OLLAMA_CONTEXT_LENGTH` = 8192, `OLLAMA_KEEP_ALIVE` = −1, `LLM_TIMEOUT_S` = 300.** Промпт агента з 12 кандидатами перевищує типове контекстне вікно Ollama, а надлишок вона обрізає без попередження. Модель лишається в пам'яті між запитами. Інференс локальної моделі на CPU може тривати кілька хвилин.
- **GPU — окремий файл `compose.gpu.yaml`.** Потрібен NVIDIA Container Toolkit (Docker Desktop з WSL2 на Windows). Без нього `docker compose up` працює на CPU; рекомендовано 16 ГБ оперативної пам'яті. Для менш потужної машини передбачено `OLLAMA_MODEL=gemma4:e2b`.
